# Interface language — the i18n layer

Written 2026-08-05, on branch `feat/i18n-multilanguage`. This file is the **contract the port
executes against**: the foundation phase builds exactly what is described here, seven port agents
then move strings mechanically, and the acceptance phase checks the two invariants at the end.

Read [`CLAUDE.md`](../CLAUDE.md) first. Its locked decisions and gotchas explain why the code looks
the way it does, and decision 8 ("German-first content") is the one this document splits in two.

- **905** user-visible strings in `apps/web/src`, **~210** in `apps/api/src` + `packages/shared/src`
  (the inventory's 156 was low — see §9), **80** German doc comments. 95 + 71 files.
- Two locales: `de` (today's copy, byte-identical) and `en` (new).
- No new runtime dependency. ~350 lines of typed runtime, the rest is data.

**Reviewed 2026-08-05, after the plan was written and before the foundation was built.** Fourteen
corrections came out of that review; each one is marked **[R]** where it lands, and where it overrules
the original decision the original is kept with the reason it lost. Three of them were blocking:
`formatDuration()` (§7 and rule 10), the wire-key fallback (§2/§4) and acceptance check 1, which
failed its own worked example (§11).

## 0 — The one distinction everything else depends on

There are two "languages" in this app and they are not the same axis.

| | **Interface language** | **Content language** |
| --- | --- | --- |
| What it is | UI copy, error text, validation text, date/number formatting | The language a *recipe* is written in, and the German vocabulary that parses it |
| Chosen by | the viewer, at runtime, per device | the recipe, at import time; the deployment, for OCR |
| Lives in | this i18n layer | `packages/shared/src/{units,ingredients,numbers,text}.ts`, `duration.ts`'s **parse** half **[R]**, `recipes.language`, `TESSERACT_LANGS`, the importer's outbound `Accept-Language`, `foldSql()`, `recipes.*_fold` |
| Changes when | the user picks English | never, unless the recipe changes |

A German household running the app in English still stores `250 g Mehl`, still parses `2-3 Eier`,
still folds `Müsli` to `muesli` for search, and still asks chefkoch.de for a German page. **Nothing
in the content-language column is touched by this work** beyond translating its comments to English.

`FOLD_PAIRS` in particular is deliberately half-finished for a documented SQLite reason — read that
gotcha before going near it, and do not add a pair. `recipes.language` is not the UI locale and must
never be wired to one; `formState.ts` keeps hardcoding `language: "de"` for a recipe typed into the
German-shaped form.

**Borderline cases have one rule: a string is interface language until it is SAVED.** The default
shopping-list name (`"Einkaufsliste"`), the duplicate-title suffix (`" (Kopie)"`) and the servings
fallback unit (`"Portionen"`) are UI copy at the moment the UI produces them, and plain content
afterwards. They get catalog keys, and **a stored value is never re-translated on read** — a list
created as "Einkaufsliste" stays "Einkaufsliste" for a viewer who switched to English, because by
then it is the name the group gave it.

**[R] That rule has one exception, and it points the other way: text the SERVER generates INTO a row.**
`services/import/parsed.ts` composes `Nährwerte (pro Portion): …` and folds it into the draft's notes.
The rule as written above would render it in the requester's negotiated locale — so importing a German
chefkoch page with the UI set to English would write an English sentence into the middle of a German
recipe, permanently. Server-side text that is persisted renders in `env.defaultLocale`, never in
`requestLocale(c)`; the recipe's own `language` is the better source the day drafts carry a reliable
one. The distinction is *who* is producing the string: a user typing into their own UI (the list name,
the `(Kopie)` suffix) follows their locale, a server composing content follows the content's. See
rule 11.

**[R] And one surface that looks like content and is not: `formatDuration()`.** It lives in
`packages/shared/src/duration.ts` next to `parseDuration()`, but it *renders* — "0 Min.", "1 Tag" /
"2 Tage", "3 Std.", "35 Min." — German words this codebase generates, not German words it reads out of
a recipe. It reaches the screen through `lib/format.ts`'s `formatMinutes()` and directly in
`ParsedRecipeEditor`. Left on the never-touch list (where the first draft of this plan put it, because
the *file* is a content file) an English UI would print "1 Std. 35 Min." on every recipe card, and
acceptance check 2 would not notice because the file is allow-listed. §7 splits the file's two halves.

## 1 — Where the layer lives

**Decision. Split by what each side needs, along the line `packages/shared` already draws.**

```
packages/shared/src/i18n/     the pure runtime + the SERVER catalog (errors, validation, mail)
apps/web/src/lib/i18n/        the React binding + the six UI catalogs + the locale store
```

`packages/shared` gets the runtime because three consumers need it and only one of them is a
browser: the API renders error and mail copy, the web app renders UI copy, and **the Zod error
messages are produced by schemas both sides run**. The runtime is pure — `Intl.PluralRules`,
`Intl.NumberFormat` and string work only. No React, no `window`, no `document`, no `localStorage`,
no `process`. That is checked by the existing rule in `packages/shared/src/index.ts` ("Never import
node/bun APIs here") and by the fact that `apps/web` bundles it.

`apps/web/src/lib/i18n/` gets everything that is a browser or React concern: the provider, the
`useT()` hook, the ambient locale store, `localStorage` persistence, `<html lang>`, and the six
catalogs of UI copy. UI copy is **not** part of the API contract, so it does not belong in a package
whose stated job is "the single source of truth for every request/response shape".

*Rejected: everything in `packages/shared`.* It would put ~900 strings of button labels into the
contract package and make the API bundle carry the web app's copy for no reason.
*Rejected: everything in `apps/web`.* The API cannot import from `apps/web`, so the error and Zod
messages would have to be duplicated — and the whole point of running the same schema on both sides
is that they cannot drift.

## 2 — Catalog shape and typing

**Decision. Flat keys, dotted, prefixed with the namespace. One object literal per namespace per
locale. `de` declares the type; `en` is checked against it.**

```ts
// apps/web/src/lib/i18n/catalogs/shopping.de.ts
import type { NamespaceCatalog } from "@toon/shared";

export const shoppingDe = {
  "shopping.lists.title": "Einkaufslisten",
  "shopping.lists.empty": "Noch keine Liste.",
  "shopping.list.defaultName": "Einkaufsliste",
  "shopping.list.itemCount": { one: "{count} Position", other: "{count} Positionen" },
  "shopping.item.removeLabel": "{name} entfernen",
} as const satisfies NamespaceCatalog<"shopping">;

export type ShoppingKey = keyof typeof shoppingDe;
export type ShoppingCatalog = typeof shoppingDe;
```

```ts
// apps/web/src/lib/i18n/catalogs/shopping.en.ts
import type { LocaleCatalog } from "@toon/shared";
import type { ShoppingCatalog } from "./shopping.de";

export const shoppingEn: LocaleCatalog<ShoppingCatalog> = {
  "shopping.lists.title": "Shopping lists",
  "shopping.lists.empty": "No list yet.",
  "shopping.list.defaultName": "Shopping list",
  "shopping.list.itemCount": { one: "{count} item", other: "{count} items" },
  "shopping.item.removeLabel": "Remove {name}",
};
```

**Flat, not nested.** `keyof` is then a plain string union, the de/en parity type is one mapped
type, `grep "shopping.list.itemCount"` finds every use, and two agents adding keys to the same file
touch different lines. *Rejected: nested objects with a recursive `Path<T>` type* — slower to
typecheck, unreadable errors, and it makes a port agent think about tree structure inside a file
instead of about strings.

**The namespace prefix is enforced by the type**, which is what makes seven parallel ports safe
without a shared registry of keys:

```ts
export type NamespaceCatalog<Prefix extends string> = Record<`${Prefix}.${string}`, CatalogEntry>;
export type CatalogEntry = string | PluralForms;
export type PluralForms = { readonly other: string } &
  { readonly [C in Exclude<Intl.LDMLPluralRule, "other">]?: string };
```

Prefixes are disjoint, so **two namespaces cannot collide on a key** and the merge in
`catalogs/index.ts` is order-independent. A runtime test asserts it anyway (cheap, and it catches a
hand-edited prefix).

**`tsc` catches a key that exists in `de` but not in `en`** through `LocaleCatalog`:

```ts
export type LocaleCatalog<C extends Record<string, CatalogEntry>> = {
  readonly [K in keyof C]: C[K] extends string ? string : PluralForms;
};
```

- A key missing from `en` → *Property 'shopping.lists.empty' is missing in type* (mapped types are
  not optional).
- A key only in `en` → excess-property error, because `shoppingEn` is an annotated const, not a
  `satisfies`.
- A key that is a plural object in `de` but a plain string in `en` → type error, and vice versa.
- A locale may list *more* plural categories than another (`other` is the only required one), which
  is what keeps the type usable when a third locale with `few`/`many` arrives.

**A missing key at runtime** returns the key itself and warns once per key in development
(`import.meta.env.DEV` on web, `NODE_ENV=development` on the API). It never throws — an i18n miss
must degrade to an ugly label, never to a blank screen inside `ErrorBoundary`. With the types above
the only way to reach it is a cast or a dynamic key, so:

**Dynamic keys are built as template literals, never cast.** `t(\`ui.difficulty.${difficulty}\`)`
typechecks because `difficulty` is `"einfach" | "mittel" | "schwer"` and the three keys exist.
`t(someString as MessageKey)` is banned. Note what that example says about the interface/content
line: the map *keys* (`einfach`, `mittel`, `schwer`) are wire and DB values and are locked; only
their labels are copy.

**[R] There is exactly ONE key that arrives as an untyped string, and it needs a real escape hatch, not
a cast:** `details[].i18n.key` off the wire (§4) is `z.string()`, because the server that minted it may
be NEWER than the bundle reading it. Casting it to `MessageKey` and calling `t()` would hit the
missing-key path, and missing-key behaviour is *return the key* — so a version skew would paint
`server.zod.field.name.too_small.8` into a form field, throwing away the perfectly good German or
English sentence the same payload carried in `message`. That is a worse bug than the one the `i18n`
field exists to fix. So the runtime exports

```ts
export function hasKey(catalog: Record<string, CatalogEntry>, key: string): boolean;
/** Resolves a key that came off the wire. `undefined` when this bundle does not know it. */
export function resolveWireKey(locale: Locale, key: string, values?: MessageValues): string | undefined;
```

and every wire-key consumer is `resolveWireKey(...) ?? issue.message`. `resolveWireKey` is the only
sanctioned way to translate a `string`; a cast to `MessageKey` stays banned everywhere else.
*Rejected: `translate(key as MessageKey)` with the missing-key fallback doing the work* — its fallback
returns the key, which is precisely the failure mode.

## 3 — Interpolation and plurals

**Decision. Named `{placeholder}` interpolation, placeholder names inferred from the German literal
by the type system. Plurals as explicit category objects, selected with `Intl.PluralRules`.**

```ts
export type MessageValues = Readonly<Record<string, string | number>>;

/** Placeholder names in a catalog literal: Placeholders<"Remove {name}"> = "name". */
export type Placeholders<S extends string> =
  S extends `${string}{${infer Name}}${infer Rest}` ? Name | Placeholders<Rest> : never;

export type ValuesFor<E extends CatalogEntry> = E extends string
  ? { readonly [K in Placeholders<E>]: string | number }
  : { readonly count: number } &
    { readonly [K in Exclude<Placeholders<E["other"]>, "count">]: string | number };

/** No placeholders -> no second argument; otherwise it is required. */
export type TranslateArgs<E extends CatalogEntry> =
  [keyof ValuesFor<E>] extends [never] ? [] : [values: ValuesFor<E>];

export interface Translator<C extends Record<string, CatalogEntry>> {
  <K extends keyof C & string>(key: K, ...args: TranslateArgs<C[K]>): string;
}
```

So `t("shopping.lists.title")` compiles, `t("shopping.item.removeLabel")` does not (missing
`{name}`), and `t("shopping.list.itemCount", { count: n })` is the only way to call a plural entry.
**A placeholder typo is a compile error**, which is the whole reason to pay for the inference.

All four guarantees above were verified against TypeScript 7.0.2 before this plan was written:
a missing `en` key is TS2741, an extra one TS2353, a `string` where `de` has plural forms TS2322, a
wrong namespace prefix TS2353, and the three bad `t()` calls in §12 all fail.

*Budget and escape hatch.* `bun run typecheck` is **0.8 s** today for all three projects. If the
inference pushes it past ~5 s, replace `TranslateArgs<E>` with `[values?: MessageValues]` in
`types.ts` — a strictly looser type, so **every existing call site still compiles** and the change
is one line. Do not restructure catalogs to chase typecheck time.

**Plurals use `Intl.PluralRules`, not a two-form helper.** `format.ts`'s
`plural(count, "Position", "Positionen")` is **deleted**, and its 15+ call sites become plural
catalog entries. The helper works for de/en by accident (both have exactly `one`/`other`) and its
signature forces the *call site* to know the language's word forms, which is precisely what has to
move into the catalog. Selection: `pluralRulesFor(locale).select(count)` → category → the entry's
form for that category, falling back to `other`; then interpolate, so `{count}` works inside the
chosen form.

*Rejected: an ICU MessageFormat dependency (`intl-messageformat`, `@formatjs/*`).* It is a runtime
parser and ~40 KB for a feature set (gender, select, nested plurals, date skeletons in messages) that
none of the 905 strings needs. This repo hand-rolls argon2 via `Bun.password` and an SMTP client over
`node:net`; a message-format parser is not where it should start taking weight.
*Rejected: `Intl.PluralRules` with implicit `_one`/`_other` key suffixes.* Sibling keys cannot be
type-checked as a set; an object value can.

**No markup in a catalog value.** `t()` returns a string. Where a sentence needs an inline element,
the emphasised part becomes a `{placeholder}` and loses its styling, or the sentence is split into
whole independent sentences — never into fragments that get concatenated. There is exactly one
affected string today (`ImportPage`'s "Getestet mit **chefkoch.de** und **biancazapatka.com**." →
one key with `{first}`/`{second}`, the two `font-medium` spans dropped). That is the single accepted
visual change in this whole port, and it is listed here so it is not a surprise in review.
*Rejected: a `<Trans>`-style node interpolator.* Real machinery, one caller.

**German quotation marks are part of the string.** `„{name}“ neu anlegen` in the de catalog,
`Create “{name}”` in en. Never hardcode the glyphs in JSX around a placeholder — that is the same
mistake as concatenation.

## 4 — The API error contract

The envelope `{ error: { code, message, details? } }` and every value in `ERROR_CODES` are **locked**
and do not change. What changes is where `message` comes from.

**Decision: (c) both, with an explicit division of labour.**

1. **`message` is server-rendered in a negotiated locale** and stays the string a client displays.
   Negotiation order: the request's `Accept-Language` → `env.defaultLocale` (`DEFAULT_LOCALE`,
   default `de`).
2. **`code` stays the machine contract** and keeps driving client *behaviour* (`isUnauthorized`,
   the `reset_token_invalid` branches in `ResetPasswordPage`, `oauthErrorMessage()`), plus the few
   places the client deliberately words things itself (network failure, the import hints).
3. **`validation_failed` details gain a structured `i18n` field** so a form can re-render field
   errors in the *client's* locale regardless of what the server negotiated.

The web client sends `Accept-Language: <active locale>` on every request from `lib/api.ts` (and from
the one XHR in `features/import/lib/importApi.ts`). `Accept-Language` is a CORS-safelisted request
header, so this adds **no preflight and no CORS change** — which is exactly why it was chosen over a
custom `X-Toon-Locale` header (a new `allowHeaders` entry plus an OPTIONS round trip on every dev GET)
and over a `toon_locale` cookie (a second stored copy of the same preference, and in dev the web
origin's cookie never reaches the API origin anyway).

*Rejected: (a) alone — `message` becomes an English developer string and the client maps `code`.*
`code` is coarser than the copy: one `not_found` backs "Rezept nicht gefunden", "Tag nicht gefunden",
"Liste nicht gefunden". Client-side mapping from `code` alone would flatten all of them to
"Nicht gefunden", which is a copy regression, or force a parallel key space in the web catalogs that
duplicates the server's and can drift from it.

### What each caller sees

| Caller | Sends | Gets in `message` |
| --- | --- | --- |
| `curl -s localhost:3001/api/…` | nothing | **German, byte-identical to today.** The README smoke test is unchanged. |
| `curl -H 'Accept-Language: en'` | `en` | English |
| Current PWA bundle | `Accept-Language: de`/`en` from the active UI locale | the user's chosen language, always |
| **Old cached PWA bundle** | the browser's own `Accept-Language` | **[R]** the BROWSER's language, which is not necessarily today's answer. Today the header is ignored and every client gets German; after this change an old bundle on an English-configured phone gets English error text inside its still-German UI. Bounded and self-correcting — the worker swaps within ≤30 min / at the next launch (`lib/pwa.ts`) — but it is a real mixed-language window for the common "German household, English phone" setup, and the first draft of this table wrongly called it "today's behaviour". |
| **Top-level navigation** (OAuth start/callback, a mailed reset or confirm link, the invite landing page) | the browser's own `Accept-Language` — the app's choice cannot ride on a document navigation | **[R]** whatever the browser asks for. So **a response to a navigation must convey a `code`, never a rendered sentence**: `GET /oauth/:provider` already redirects with `?error=oauth_not_configured` and lets the client word it, and that is the pattern every navigation response has to keep. |
| A third-party client | whatever it sends | its language, or German |

`Error.message` on the server (logs, stack traces, `console.error` in `onErrorHandler`) is always the
**English** rendering, so ops output is one language regardless of who made the request.

*[R] Rejected as a cure for the old-bundle row: negotiating only from a header the app itself would
send* (a bare `de`/`en` with no q-list, ignoring any browser-shaped `de-DE,de;q=0.9,…`). It would pin
an old bundle to `env.defaultLocale` and remove the window entirely — and it makes
`Accept-Language: en-GB` from a legitimate third-party client mean German, which is a worse contract
than a 30-minute skew. *Also rejected: preferring the signed-in `users.locale` over the header.* It
fixes only users who have already switched once, and it inverts the device-preference model the rest
of §6 is built on.

### Shape

```ts
// packages/shared/src/schemas/common.ts  (next to ApiErrorSchema)
export const ValidationIssueSchema = z.object({
  path: z.string(),
  code: z.string(),
  /** Rendered in the locale the request negotiated. Display this if you cannot use `i18n`. */
  message: z.string(),
  /** Structured form, so a client can render the issue in ITS active locale. */
  i18n: z
    .object({
      key: z.string(),
      values: z.record(z.string(), z.union([z.string(), z.number()])).optional(),
    })
    .optional(),
});
export type ValidationIssue = z.infer<typeof ValidationIssueSchema>;
```

`details` was already `z.unknown()`, and today's consumer (`apiFieldErrors` → `fromIssues`) reads
`path` + `message`. Adding a field is backwards-compatible in both directions: an old client ignores
`i18n`, a new client falls back to `message`.

**[R] `path` is a `string` on the wire and `fromIssues` reads it as an ARRAY, and that mismatch is
pre-existing.** `toApiError()` sends `issue.path.join(".")`; `fromIssues` tests `Array.isArray(record.path)`
and otherwise keys the entry `_form`. So **every server-side 422 currently lands on `_form`, never on a
field** — the web test that proves per-field mapping feeds it `path: ["title"]`, a shape this server has
never produced. `ValidationIssueSchema` keeps `path: z.string()` (it is what is on the wire) and
`fromIssues` accepts **both** shapes. Say so out loud in the port report, because it is a behaviour
change riding along in a copy refactor: field errors from the server will start appearing under their
fields instead of in the form-level panel. If that turns out to change a screen for the worse, keep the
string branch mapping to `_form` and file it — do not silently improve it.

### `ApiError` becomes key-carrying

```ts
// apps/api/src/lib/errors.ts
import { DEFAULT_LOCALE, type Locale, type MessageValues, type ServerKey, serverText } from "@toon/shared";

export type ErrorText = ServerKey | { key: ServerKey; values: MessageValues };

export class ApiError extends Error {
  readonly status: number;
  readonly code: ErrorCode | string;
  readonly details?: unknown;
  readonly text: ErrorText;

  constructor(status: number, code: ErrorCode | string, text: ErrorText, details?: unknown) {
    super(serverText("en", text)); // English: this is what lands in the log
    this.name = "ApiError";
    this.status = status;
    this.code = code;
    this.text = text;
    this.details = details;
  }

  toBody(locale: Locale = DEFAULT_LOCALE): ApiErrorBody {
    const message = serverText(locale, this.text);
    return { error: this.details === undefined ? { code: this.code, message } : { code: this.code, message, details: this.details } };
  }

  static notFound(text: ErrorText = "server.error.notFound"): ApiError {
    return new ApiError(404, "not_found", text);
  }
  // …the other ten helpers, same shape: the German default becomes a key
}
```

Because `ServerKey` is a union of the keys in `server.de.ts`, **every call site that still passes a
German sentence is a compile error until it is ported.** That is the port's guard rail:
`bun run typecheck` enumerates the remaining work. Note the runtime consequence, and that it is
deliberate: an unported site still *works*, because a missing key resolves to itself and the key it is
handed is the German sentence. Nothing but `tsc` will tell you the port is incomplete — no test goes
red, and an `en` client silently gets German from an unported site.

**[R] `ErrorText` has no home for text this codebase did not write, and `toApiError` needs one.** Two
call sites pass a string that is not ours to key:

- `toApiError`'s `HTTPException` branch forwards `error.message` — an arbitrary string from Hono's
  internals. It **is dropped**: the envelope gets `server.error.requestFailed` and the original goes to
  the log. That is also the safer reading, since a framework message can carry internals.
- `services/import/url/fetch.ts` interpolates a REMOTE server's HTTP status into the sentence
  (`Die Seite antwortete mit ${response.status} …`). That is a normal `{ key, values: { status } }` —
  the status is a value, not text.

*Rejected: a third `ErrorText` variant `{ literal: string }` for pass-through text.* It typechecks
everywhere, so within a week it is the escape hatch that keeps German sentences in handlers, and the
compile error that drives this whole port stops firing.

```ts
// apps/api/src/lib/locale.ts
export const localeMiddleware: MiddlewareHandler<AppEnv> = async (c, next) => {
  c.set("locale", negotiateLocale(c.req.header("accept-language"), env.defaultLocale));
  await next();
};
/** Falls back to the configured default if the middleware did not run (onError can fire early). */
export function requestLocale(c: Context<AppEnv>): Locale {
  return c.get("locale") ?? env.defaultLocale;
}
```

**[R] `AppVariables.locale` is declared OPTIONAL (`locale?: Locale`).** `onError`/`notFound` really can
fire before an `app.use("*")` middleware has run, so the `??` above is load-bearing; typing the variable
as non-optional would make it read as dead code and invite someone to delete it.

Mounted in `src/index.ts` with `app.use("*", localeMiddleware)` **before** the routers, so
`onErrorHandler` and `notFoundHandler` can both read it. `notFoundHandler`'s message becomes
`{ key: "server.error.routeUnknown", values: { method, path } }`.

## 5 — Zod messages

~96 constraint sites in `packages/shared/src/schemas`, of which **15 carry a German literal** and the
rest fall through to Zod's built-in English defaults. Today `zodFieldErrors()` (browser) and
`toApiError()`'s `ZodError` branch (server) both forward `issue.message` verbatim — which is why the
validation surface is already inconsistently bilingual, and why a fix has to happen at the issue
level rather than per schema.

**The hard constraint comes from Zod 4's precedence.** `finalizeIssue()` resolves a message as

```
iss.message  ??  inst.def.error(iss)  ??  ctx.error(iss)  ??  config.customError(iss)  ??  config.localeError(iss)
```

A message attached to a check (`.min(1, "Name fehlt")`) sits in `inst.def.error` and therefore
**beats a per-parse error map**. So as long as a literal lives in the schema, no locale layer can
override it. And a per-parse map is the only per-request-safe option on the server (a module-global
"active locale" would be a cross-request data race across `await` points). Conclusion: **the literals
must leave the schemas, and the message must be produced after the parse.**

**Decision. Two channels, each unambiguous, both resolved by one pure function in
`packages/shared/src/i18n/zod.ts`.**

**(a) Built-in checks carry no message at all.** The resolver derives a key from the issue's own
structured fields, which Zod 4 provides: `code`, plus `origin`/`format`/`expected`, plus
`minimum`/`maximum`, plus `path`.

```ts
// before
name: z.string().trim().min(1, "Name fehlt").max(120),
password: z.string().min(8, "Passwort muss mindestens 8 Zeichen haben").max(200, "Passwort ist zu lang"),
url: z.url("Bitte eine gültige URL angeben").max(2000),
// after
name: z.string().trim().min(1).max(120),
password: z.string().min(8).max(200),
url: z.url().max(2000),
```

```ts
/** Key candidates for one issue, most specific first. The first one in the catalog wins. */
export function zodIssueKey(issue: $ZodIssue): { key: ServerKey; values: MessageValues } {
  // [R] The LAST NON-NUMERIC segment, not path.at(-1): an array element's path tail is its INDEX.
  // Verified against zod 4.4.3 — `tags: z.array(z.string().min(1))` fails with path ["tags", 0],
  // which as a field name gives `server.zod.field.0.too_small.1`. Walk back past every integer
  // segment; if nothing is left, the field is "".
  const field = lastNamedSegment(issue.path);            // "name", "password", "tags", ""
  const bound = "minimum" in issue ? issue.minimum : "maximum" in issue ? issue.maximum : undefined;
  const facet =                                           // the second axis, per code
    issue.code === "invalid_format" ? issue.format
    : issue.code === "invalid_type" ? issue.expected
    : "origin" in issue ? issue.origin
    : "_";
  const candidates = [
    bound !== undefined ? `server.zod.field.${field}.${issue.code}.${bound}` : undefined,
    `server.zod.field.${field}.${issue.code}`,
    `server.zod.${issue.code}.${facet}`,
    `server.zod.${issue.code}`,
    "server.zod.fallback",
  ];
  // …first candidate present in SERVER_CATALOGS.de wins; values = { field, bound, facet }
}
```

The `.${bound}` step is not decoration: `PasswordSchema` is `.min(8)` while `LoginRequest.password`
is `.min(1)`, same field name, different message. `server.zod.field.password.too_small.8` =
"Passwort muss mindestens 8 Zeichen haben"; the login one falls through to
`server.zod.too_small.string` = a generic German sentence. Field-name keys (`name` → "Name fehlt",
`title` → "Titel fehlt", `color` → the hex sentence) reproduce today's German exactly, and they also
give the ~80 sites that render **English** today a proper German message — a fix, not a parity
break (see §11).

**[R] Understand what inference buys and what it costs.** `(field, code, bound)` is now the identity of
a message, so two constraints that share all three CANNOT have different copy. Today that is a
non-issue and in one place it is a win: `min(1)` on a `name` carries "Name fehlt" at four sites
(`group.ts:71`, `shopping.ts:92/97/107`) and no message at five more (`group.ts:78`, `recipe.ts:23/182/197`,
`shopping.ts:127`), and after the port all nine say "Name fehlt" — including the ingredient row inside a
recipe, whose path tail is also `name`. Check that reads acceptably per field before writing the key.
Where it does not, the answer is an explicit `refineKey`-style key on that one check, never a second
inference axis.

**(b) Custom refinements carry an explicit key** in `params`, which Zod 4 puts on the issue
(`$ZodIssueCustom.params`) and which therefore survives into `details` on the wire. Inference is
wrong here: a `.refine()` has no `origin` and often an empty `path`, so all five
"Keine Änderungen übergeben" guards and `HttpUrlSchema`'s protocol check would key identically.

```ts
// packages/shared/src/i18n/zod.ts
export function refineKey(key: ServerKey): { params: { i18n: ServerKey } } {
  return { params: { i18n: key } };
}
// packages/shared/src/schemas/common.ts
export const HttpUrlSchema = z.string().max(2000)
  .refine(isHttpUrl, refineKey("server.validation.httpUrlOnly"));
// packages/shared/src/schemas/group.ts
export const UpdateGroupRequestSchema = z.object({ … })
  .refine((value) => Object.keys(value).length > 0, refineKey("server.validation.noChanges"));
```

`refineKey` is a **type-only dependency on the key union plus a plain object literal** — no locale is
read, nothing is resolved, nothing is imported that touches `Intl`. The schemas stay locale-free at
module-eval time, which is the constraint.

**Resolution, one function, both sides:**

```ts
export function resolveZodIssue(issue: $ZodIssue, locale: Locale): { message: string; key: ServerKey; values: MessageValues };
export function toValidationIssues(error: $ZodError, locale: Locale): ValidationIssue[];
```

- Server: `toApiError()`'s ZodError branch → `ApiError.validationFailed(toValidationIssues(error, locale))`.
- Browser: `zodFieldErrors()` → `resolveZodIssue(issue, getLocale()).message` for a local
  `safeParse`; `apiFieldErrors()` → `issue.i18n` first, `issue.message` second.

Both call the same resolver over the same catalog, so a field that fails client-side and again
server-side reads identically.

Resolution happens **after** the parse, on the finished `ZodError`, not via a per-parse error map —
otherwise every one of the 100+ `parse()`/`safeParse()` call sites would have to thread a locale.
That works because Zod 4 keeps the structured fields on the issue: verified against zod 4.4.3,
`too_small` carries `origin`/`minimum`/`inclusive`/`path` and a `.refine(fn, { params })` carries
`params` straight through to `error.issues[i]`. `issue.message` still holds Zod's built-in English
default; the resolver ignores it, and it survives only as what a non-localising consumer of a raw
`ZodError` (a script, a test) would print.

**Type inference is untouched.** A check's message never appears in `z.infer` or `$inferInsert`;
deleting a string argument changes no type. The `refineKey()` object is a `params` bag, not a schema
change. `packages/shared/test/schemas.test.ts` asserts no messages today, so nothing there breaks.

## 6 — Locale negotiation and persistence

**Decision. The interface locale is a DEVICE preference (`localStorage`), mirrored per account
(`users.locale`) only because mail is delivered outside any browser.**

```
web:  localStorage["toon.locale"]  ->  navigator.languages  ->  DEFAULT_LOCALE ("de")
api:  Accept-Language              ->  env.defaultLocale (DEFAULT_LOCALE, default "de")
mail: users.locale                 ->  env.defaultLocale
```

- `toon.locale` joins `storageKeys` in `lib/storage.ts` (private-mode-safe, same as `toon.theme`).
- **[R]** `main.tsx` calls **`initLocale(resolveDeviceLocale())`** next to `applyTheme(...)`, before
  `createRoot`. `initLocale` does two things — seed the module store **and** set `<html lang>`. The
  first draft called `applyDocumentLocale(resolveDeviceLocale())`, which only sets the attribute: the
  store would have stayed at its `DEFAULT_LOCALE` initialiser, so a device that resolved `en` would
  have rendered `lang="en"` and German copy. `initLocale` deliberately does **not** write storage and
  does **not** PATCH the API — it is reading a preference, not setting one. `setLocalePreference()` stays the
  user action.
- Picking a locale writes `localStorage`, updates the store (re-render), sets
  `document.documentElement.lang`, and — when signed in — fires `PATCH /api/auth/me { locale }` so
  mail follows. A failed PATCH is not fatal: the UI is already switched. **[R]** It must therefore be
  a fire-and-forget `void … .catch(() => undefined)` and **not** a TanStack mutation: offline it would
  pause, and a paused non-shopping mutation is not persisted by `shouldPersistMutation` anyway, so
  queueing it buys nothing and risks an unhandled rejection on a locale switch in airplane mode.
- **[R] A DOM-free seam for tests.** `setLocalePreference()` touches `localStorage`, `document` and the network,
  and `bun test` has none of the three (`apps/web/src/**/*.test.ts` are plain pure-function tests, no
  happy-dom). The store therefore also exports `setLocaleForTest(locale)` — store only, no side
  effects — and it obeys the same handback rule as `setMailer`/`setOcrEngine`: **a test file that calls
  it MUST reset it in `afterAll`**, because `bun test` runs every file in one process and a module-global
  left on `en` is inherited by every later file. See rule 13.
- The switcher lives on `/settings` next to the theme control (namespace `auth`, since
  `AccountSettingsPage` is that agent's file).

**A locale change does NOT need a reload.** All catalogs for all locales are statically imported and
bundled, so `setLocalePreference()` is synchronous: no async import, no suspense boundary, no loading state,
and **switching works offline** — which matters for the one feature that is editable offline. Cost:
both locales ride in the main chunk, ~2 × 36 KB raw / ~20 KB gzipped total. *Rejected: a dynamic
`import()` per locale.* It buys ~10 KB gzipped and pays with a boot-order hazard in an installed PWA
(the chunk is precached, but a first switch on a cold offline start is exactly the case where a
missing chunk lands in `ErrorBoundary`). Revisit only if a third locale lands: the fix then is to
preload the chunk *before* rendering, never to suspend mid-tree.

### The three things it must not break

1. **The per-user persisted TanStack cache (`lib/persist.ts`).** No interaction, deliberately: the
   cache holds *data* (recipes, lists, `/api/auth/me`) and queued mutation *variables* (item names) —
   content, not copy. Server-rendered `message` strings live on errors, and errors are never
   persisted. So a locale change purges nothing, and **`PERSIST_BUSTER` must NOT be bumped**: busting
   the blob would discard the queued offline shopping writes it also carries. Adding `locale` to
   `UserSchema` is safe for an already-persisted blob because the field is nullish.
2. **The service worker.** Catalogs are part of the hashed `assets/*.js` precache, versioned with the
   bundle. **No new `runtimeCaching` entry, no change to `navigateFallbackDenylist`**; `/api` and
   `/uploads` stay uncached. Because `Accept-Language` now varies per user while `/api` is never
   cached by the SW, there is no `Vary` trap — but do not add a runtime cache for `/api` later
   without remembering that error bodies are now locale-dependent.
3. **`<html lang>` / `<meta theme-color>` / the manifest.** `lang` is owned at runtime by
   `applyDocumentLocale()` (called from `initLocale`/`setLocalePreference`), exactly as `theme-color` is owned by
   `lib/theme.ts`; `index.html` keeps `lang="de"` as the pre-JS default. **[R] `document.title` is
   OUT OF SCOPE and stays `<title>Rezepte</title>`.** Nothing in `apps/web/src` sets it today — the
   first draft said "set by the shell from a catalog key", which contradicted this same paragraph's rule
   that the app NAME is brand and is not translated, and would have added per-screen titles nobody asked
   for. What stays German and build-time: the **PWA manifest** (`name`/`short_name` are
   the brand "Rezepte" and are not translated at all; `description` and `lang: "de"` cannot be
   per-locale in a single manifest), `index.html`'s `<meta name="description">`, and the `<noscript>`
   sentence — a string shown only when JS is off cannot be localised by JS. Documented limitation,
   not an oversight; a per-locale build split is not worth a second image.

`users.locale` is `text`, **nullable**, no default: NULL means "never chosen", which is what lets
`env.defaultLocale` win for an install that changed its default. It is a new column, so
`bun run db:generate` + one migration — and when drizzle-kit offers to "fix" the `*_fold` columns'
`DEFAULT ''` divergence, **decline** (existing gotcha).

## 7 — Formatting

`lib/format.ts` has three `Intl` constructors and one `toLocaleString`, all hardcoded `de-DE`, and it
is imported by nearly every feature. They are module-level singletons because constructing an `Intl`
formatter is expensive (tens of µs, and a recipe list formats 24 dates).

**Decision. Keep the call sites exactly as they are. Make the formatters per-locale singletons in a
`Map`, resolved through an ambient locale that only the web app has.**

```ts
const cache = new Map<Locale, Formatters>();
function formatters(): Formatters {              // getLocale() from lib/i18n/store
  const locale = getLocale();
  let entry = cache.get(locale);
  if (!entry) { entry = build(INTL_LOCALE[locale]); cache.set(locale, entry); }
  return entry;
}
export function formatDate(iso: string | null | undefined): string { … formatters().date.format(date) }
```

At most one formatter set per locale for the lifetime of the document, no construction per render,
and `formatDate(iso)` keeps its signature — so none of the ~100 call sites change.

**An ambient locale is safe in the browser and forbidden on the API.** One document is one user is
one locale; a Bun server process is many users, so the API always passes `locale` explicitly
(`requestLocale(c)`, `toBody(locale)`, `inviteMail({ …, locale })`). That asymmetry is deliberate and
is the reason there are two entry points:

- **`useT()` inside React** — subscribes to the store, so a locale switch re-renders. Components must
  use this.
- **`translate()` outside React** — reads the ambient locale once. Only for `lib/api.ts` fallbacks,
  toasts fired from event handlers, thrown messages, and `ErrorBoundary` (which must not depend on a
  context that may be the thing that broke).

A component that calls `translate()` in its body renders stale copy after a switch. That is the one
rule a port agent can get wrong silently — it is called out again in §10.

`INTL_LOCALE` maps `de → "de-DE"` and `en → "en-GB"`. *Rejected: bare `"en"`*, which resolves to
US formatting: `03/08/2026` reading as March 8th in a European kitchen is a real defect, and en-GB
also keeps the 24-hour clock the German original has. `formatBytes` uses the locale's number format
(so `1,5 MB` / `1.5 MB`); the unit letters `B`/`KB`/`MB` are not translated.

`formatRelative`'s `"gerade eben"` and `formatDate`'s `"–"` placeholder become `ui.*` keys.
`formatServingsLabel`'s `"Portionen"` fallback becomes `ui.servings.defaultUnit` and is *passed into*
`formatServings()` from `@toon/shared` — the pure formatter stays content-side and simply receives a
localised unit. `PendingDraftsList.tsx`'s local `formatDate()` and `useAutosave.ts`'s
`toLocaleTimeString("de-DE")` are **deleted** in favour of the shared helpers (a new
`formatTime()` if needed); duplicating a formatter is how one screen stays German forever.

### [R] `formatDuration()` — the one content file that has to be split

`packages/shared/src/duration.ts` holds both halves of the duration story and only one of them is
content:

| | |
| --- | --- |
| `parseDuration` / `parseServings` | reads German recipe text ("1 Std. 15 Min.", "20-25 Minuten", "für 4 Personen"). **Content. Untouched.** |
| `formatDuration` / `formatServings` | writes the string on the screen. **Interface.** |

`formatDuration` generates German words the codebase owns — `"0 Min."`, `"1 Tag"` / `"2 Tage"` (a
hand-rolled German plural), `"3 Std."`, `"35 Min."` — and it reaches the user twice: through
`lib/format.ts`'s `formatMinutes()` (recipe cards, detail, cook mode, everything) and directly in
`features/import/components/ParsedRecipeEditor.tsx`, which imports it from `@toon/shared`.

```ts
export function formatDuration(minutes: number | null | undefined, locale: Locale = DEFAULT_LOCALE): string;
```

It resolves `server.duration.zero` / `.days` / `.hours` / `.minutes` (`.days` is a plural entry — `Tag`
/ `Tage`, `day` / `days`) from `SERVER_CATALOGS`, which is already in `packages/shared` and already
carries the units-of-copy the API needs. The German values are byte-identical, and because the
parameter DEFAULTS to `de`, `packages/shared/test/duration.test.ts`'s six pinned outputs
(`[95, "1 Std. 35 Min."]`, `[0, "0 Min."]`, …) keep passing untouched. Web side: `formatMinutes()` passes
`getLocale()`, and `ParsedRecipeEditor` switches from the shared import to `formatMinutes` — a page
component has no business calling the raw formatter.

*Rejected: leaving it on the never-touch list* (the first draft did, because the *file* is a content
file). English UI, German durations on every card, and acceptance check 2 allow-lists the file so
nothing reports it. *Rejected: a label-bag parameter* (`formatDuration(m, { day, days, hours, minutes })`)
by analogy with `formatServings`'s injected unit — it works, but `formatServings` receives one unit that
often comes from DATA, whereas every one of these four labels is always ours; passing a locale is the
honest signature.

**[R] `formatQuantity` stays as it is, and that is a decision, not an omission.**
`packages/shared/src/numbers.ts:formatQuantity` renders `1,5` and `½` — German number formatting — and
it is BOTH display (`ServingsScaler`, `RecipeDetailPage`) and round-trip (it fills the ingredient and
draft inputs that `parseNumberToken` then re-reads). Localising it would mean an English UI writes `1.5`
into a field, which `parseNumberToken` does accept, but it also changes what `formatIngredient` composes
and what `recipeToPlainText` exports. Not worth the blast radius for a decimal separator. Same for
`formatIngredient` and `formatShoppingAmount`: they concatenate a number, a unit from DATA and a name —
no copy of ours. Recorded so no agent re-litigates it mid-port under rule 9.

## 8 — Mail

**Decision. `inviteMail` / `passwordResetMail` / `verifyEmailMail` take an explicit `locale`. The
recipient's `users.locale` decides; unknown falls back to `env.defaultLocale`.**

```ts
export interface PasswordResetMailInput { to: string; name: string; resetUrl: string; expiresInMinutes: number; locale: Locale }
```

They stay pure functions with no I/O — they just resolve their copy through
`createTranslator(SERVER_CATALOGS[locale], locale)` over `server.mail.*` keys, including the shared

| Mail | Locale source | If unknown |
| --- | --- | --- |
| Password reset | the user row being reset | `env.defaultLocale` |
| E-mail confirmation | the session's own user row | `env.defaultLocale` |
| **Group invite** | the **inviting** user's `users.locale` | `env.defaultLocale` |

The invite is the honest compromise: the recipient usually has no account yet, so there is no

name for the three-state `sent` / `not_configured` / `failed` contract. `POST /password/forgot` still
answers 204 for a known and an unknown address, with the rate limit before the lookup, and still
reports no delivery status. A locale is an input to the *copy*, nothing else.

**`ConsoleMailer`'s ASCII box, `smtp.ts`'s thrown connection errors, and every `console.*` line stay
English and are never localised.** They are ops output; one language in the log is a feature. That
also settles `smtp.ts`'s German "SMTP-Verbindung … fehlgeschlagen" — it becomes English, not a key.

## 10 — Port rules

Mechanical. A port agent does not make design decisions.

1. **Move, do not rewrite.** The German value in the catalog is the *exact* bytes of the literal it
   replaced, including punctuation, `„“` quotes, `…`, `–`, non-breaking spaces and trailing periods.
   If the copy reads badly, leave it and report it. Improving copy in the same pass makes the parity
   check useless.
2. **Key naming: `<namespace>.<screen-or-component>.<element>[.<variant>]`**, lowerCamelCase
   segments, no abbreviations. `auth.login.submit`, `recipes.form.title.label`,
   `recipes.form.title.placeholder`, `import.review.footer.save`, `groups.danger.deleteConfirm`,
   `ui.toast.copied`. For a component reused across screens, key by component:
   `ui.confirmDialog.cancel`. Do not key by English text.
3. **One key per sentence, never per fragment.** Any string built with `+` or a template literal
   that spans words becomes one key with named placeholders: `` `${label} verbinden` `` →
   `"auth.oauth.connect": "Mit {provider} verbinden"`. This is the rule that makes English word order
   possible; violating it is the most damaging thing in this port.
4. **Counts go through a plural entry**, never `plural()` (deleted) and never
   `` `${n} ${n === 1 ? "…" : "…"}` ``.
5. **Interpolated user data stays a value**, never pre-formatted into the sentence: `{name}`,
   `{count}`, `{email}`, `{groupName}`, `{filename}`, `{index}`. Dates and numbers are formatted by
   `lib/format.ts` first and passed in as strings.
6. **`useT()` in components, `translate()` outside React.** A `translate()` call inside a component
   body is a bug (stale copy after a switch), even though it typechecks.
7. **`aria-label`, `title`, `placeholder`, `alt`, toast text and thrown user-facing messages are
   copy** and get keys. `data-*`, `className`, query keys, route paths, mutation keys, enum values,
   error codes, storage keys and `merge_key` inputs are **not**.
8. **Enum labels: the key of the map is a domain value and is locked; only the label moves.**
   `roleLabels`, `difficultyLabels`, `SORT_LABELS`, `DIFFICULTY_OPTIONS`, `TIME_OPTIONS`,
   `RATING_OPTIONS`, `INVITE_STATUS_LABELS`, `FIELD_LABELS`, `MESSAGES`, `MAIL_OUTCOMES` and
   **[R] `NAV_ITEMS` / `SECONDARY_NAV_ITEMS`** (`components/layout/nav-items.ts` — `label: "Rezepte"`,
   `"Einkauf"`, `"Importieren"`, `"Profil"`, `"Gruppen"`, `"Sammlungen"`, `"Tags"`) become
   `Record<DomainValue, MessageKey>` / a `labelKey` field, resolved at render time — **not** module-level
   constants holding translated strings, which would freeze the locale at import time. `nav-items.ts` is
   the one CLAUDE.md calls the single source for both the phone tab bar and the sidebar, so freezing it
   freezes navigation in two places at once; `to` and `exact` are route contract and do not move.
9. **When you cannot confidently classify a string as interface or content: LEAVE IT AND REPORT IT.**
   Do not guess, do not "tidy", do not delete German vocabulary. Report the file, the line and why it
   is ambiguous. A missed string is a five-minute follow-up; a German unit table routed through the
   UI locale is a data-corruption bug that shows up as recipes that no longer parse.
10. **Never touch**, in any file: `FOLD_PAIRS`/`foldText` (`packages/shared/src/text.ts`),
    `foldSql()`, `recipes.title_fold`/`description_fold`/`name_fold`, `packages/shared/src/units.ts`,
    `ingredients.ts`, `numbers.ts`, `shopping.ts`'s key builders (the U+001F
    separator), `recipes.language` / `draft.language` / `language: "de"` in `formState.ts`,
    `TESSERACT_LANGS`, the importer's outbound `Accept-Language` in `services/import/url/fetch.ts`
    and `image.ts`, `services/import/ocr/segment.ts`'s German layout heuristics, **[R]**
    `services/import/ocr/quantity-fix.ts`, `services/import/url/schema-map.ts`,
    `services/import/url/adapters/*.ts` and `apps/api/scripts/seed.ts` (all German recipe vocabulary or
    seed content, all of which acceptance check 2 would otherwise flag), and every value in
    `ERROR_CODES` — **[R]** plus every `reason` string inside an error's `details`.
    **[R] `packages/shared/src/duration.ts` is NOT on this list any more**: `parseDuration` and
    `parseServings` are (never touch them), but `formatDuration` is interface copy and is ported. §7.
11. **Mixed files exist and are named here.** `features/import/lib/{confidence,draftEdit,importApi}.ts`,
    `features/shopping/lib/parse.ts`, `features/recipes/lib/{format,formState}.ts`,
    `services/import/{parsed,times}.ts` and **[R]** `packages/shared/src/duration.ts` all contain
    user-facing copy *next to* content-language
    logic. Port the copy (diagnostic `reasons`, `problems`/`warnings`, `FIELD_LABELS`, the
    `" (Kopie)"` suffix, `recipeToPlainText()`'s section headings), leave the parsers.
    **[R] And one sub-rule for the server half: text the server writes INTO a row renders with
    `env.defaultLocale`, never with `requestLocale(c)`.** `services/import/parsed.ts`'s
    `Nährwerte (pro Portion): …` line is folded into the draft's notes and then lives there forever;
    rendering it in the requester's UI locale would put an English sentence inside a German recipe.
    Grep for a rendered string that reaches an insert or update before you wire a locale into it.
12. **German doc comments become English**, prose only — never reword a comment to hide that the code
    is about German recipe vocabulary. `// Deutsche Einheiten zuerst` → `// German units first`, not
    `// units first`.
13. **Tests that assert copy. [R] Rewritten — the first version of this rule would not have run.**
    - **API tests switch to `error.code`** at the four message-substring sites
      (`import/ocr-disabled.test.ts:117` "Webadresse", `auth.test.ts:219` "kein Passwort",
      `import/ocr-segment.test.ts:520`, `import/url-pipeline.test.ts:68`). `import/ssrf.test.ts:286`
      ("HTTP 404") may stay: the status is a `{status}` value inside the German sentence, so the
      substring survives — switch it anyway for consistency.
    - **`smoke.test.ts:52` asserts the WHOLE envelope**
      (`{ error: { code: "email_taken", message: "E-Mail ist bereits registriert" } }`) and the
      inventory missed it. It keeps passing untouched, because `app.request()` sends no
      `Accept-Language` and `negotiateLocale` therefore returns `env.defaultLocale` = `de`. That is
      worth knowing: **the API test suite is the German-parity check for the server half**, and if it
      goes green only after you edit an assertion, you changed copy.
    - **`mail.test.ts` has eight copy assertions, not one** ("Familie", "14 Tage", "60 Minuten",
      "abgemeldet", "einmal verwendet", "bestätige", "24 Stunden"). Pass `locale: "de"` and they all
      hold, byte-identically.
    - **Web tests set NOTHING.** `apps/web/src/**/*.test.ts` run under `bun test` with no DOM, no
      `localStorage` and no server: `setLocalePreference("de")` in a `beforeEach` would throw on
      `document.documentElement.lang` and fire a PATCH at nothing. The store's initialiser is already
      `DEFAULT_LOCALE` = `de`, so `validation.test.ts`'s `"Unbekannter Fehler."` and
      `confidence.test.ts`'s `"unbekannt"` keep passing with no test change at all. A test that
      genuinely needs `en` uses `setLocaleForTest("en")` and **hands it back in `afterAll`** — same
      rule as `setMailer(null)`, for exactly the same reason (one process, filesystem file order).
    - `packages/shared/test/duration.test.ts`'s six `formatDuration` outputs stay untouched: the
      `locale` parameter defaults to `de` (§7).
14. **Report, per area**: keys added, strings left behind with reasons, anything ambiguous, and any
    string whose German value you could not reproduce byte-identically.

## 11 — German parity, and how acceptance checks it

**The rule: German copy is byte-identical to today's. This is a refactor of where strings live.**

Two exceptions, both explicit:

- **A message that is English today may become German.** ~80 Zod constraint sites render Zod 4's
  built-in English defaults right now (`"Too small: expected string to have >=1 characters"`). Those
  get proper German in `server.de.ts`. That is fixing an existing inconsistency, not breaking parity.
- **The one dropped emphasis** in `ImportPage`'s tested-sites hint (§3). The string is identical; two
  `font-medium` spans are gone.

`bun run i18n:check` (`scripts/i18n-check.ts`) runs two checks, and joins the verification gates:

**Check 1 — every German catalog value existed before.** For each value in every `*.de.ts` catalog,
split on `{placeholder}`, **[R] trim each fragment**, and require every fragment still ≥3 characters
long to appear verbatim (`String.includes`, case-sensitive, no other normalisation) somewhere in the
**base tree** — the commit this branch forked from, searched with `git grep -F <fragment> <BASE>`.
A byte-identical port makes this pass by construction; a reworded sentence, a changed dash, a
straightened quote or a lost `…` fails it. Genuinely new German (the Zod defaults above) lives in an
explicit `NEW_GERMAN` allow-list in the script, one entry per key with a one-line reason.

**[R] Two corrections, and the first one is why this check needed a review.** *Trim the fragments.*
Without it the check **fails its own worked example in §12**: `{count} Position` splits into
`" Position"` with a leading space, and the base tree contains the bare literal
`plural(list.itemCount, "Position", "Positionen")` — no space before the word — so a correct port
would have been reported as a parity break, on the very first plural entry anyone writes. *And search
the tree, not a path.* `git show <BASE>:<path>` needs a path per value, and a catalog value has no
path — the string it came from could be in any of 95 files. `git grep -F` over the base commit is the
operation that actually exists. Accept the precision this costs: a short fragment like `und ` matches
somewhere in almost any tree, so check 1 catches rewording and typography, not a sentence
reassembled out of common words. Rule 1 and review cover that; nothing grep-shaped can.

**Check 2 — no German left in ported source.** Grep the ported trees for string and JSX literals
matching `[äöüßÄÖÜ]` or a small German stopword list (`\b(der|die|das|und|nicht|dein|deine|dich|kann|
wurde|keine|bitte|noch|mehr|schon)\b`, case-insensitive), excluding: the `*.de.ts` catalogs, test
files **[R] and `apps/api/test/fixtures/**` (German recipe pages — content)**, and the content-language
allow-list from rule 10 — **[R] which now has to name `services/import/{ocr/quantity-fix,url/schema-map,
url/adapters/*,parsed,times}.ts` and `apps/api/scripts/seed.ts`, or the check drowns in false
positives on its first run and gets ignored.** Any hit is a missed string. Both checks are
`grep`-shaped on purpose — no AST, no parser to maintain.

**[R] What neither check can see.** Check 2 skips the content-language allow-list, which is exactly
where `formatDuration`'s `"Std."`/`"Min."` were hiding (§7). The residual risk is therefore
*interface copy inside an allow-listed content file*, and the only defence is the manual pass at the end
of this section: **switch to English and read every screen**, with durations, servings and quantities
specifically in view.

Plus, from the foundation tests: catalog key prefixes are correct and unique across namespaces, every
plural entry has `other`, and **the placeholder set of every key is identical in `de` and `en`** (a
translation that drops `{count}` renders a sentence with a missing number and no type error catches
it — the values type is derived from the German literal only).

## 15 — [R2] Closing the two gaps the port left, and the language picker

The acceptance audit of the original port recorded three gaps. All three are now closed; this section
is what shipped and why, in the same voice as the rest of the doc.

### The two unported files, and the workflow bug behind them

`features/import/components/ParsedRecipeEditor.tsx` (~60 strings) and
`features/import/lib/importApi.ts` (~33) came out of the port with **zero** `t()` calls. Not a
judgement error by the agent that owned `features/import`: the orchestration built each port agent's
never-edit list from the FOUNDATION's actual diff, and the foundation had touched both files (it added
the `Accept-Language` header to the one XHR, and `formatDuration`'s callers). So the import agent was
hard-forbidden from the two files carrying the most German copy in its own area, and correctly
reported them instead of crossing the line.

**The lesson for any future fan-out over this repo: a parallel agent's boundary must come from the
PLAN's namespace table, never from what an earlier phase happened to touch.** A foundation that
reaches into a feature area silently subtracts that area from its owner.

### `ImportErrorText` — the errors carry keys, not sentences

`importApi.ts` is not a component, so it cannot hold a `useT()`. The obvious fix — the ambient
`translate()` — is wrong here for a reason worth writing down: it renders at THROW time, and
`useAutosave` puts a save error into React state that can sit on screen for as long as the review page
is open. A language switch would leave a stale German sentence under an English UI.

So `ImportApiError.title`/`.hint` and `describeError()` return `ImportErrorText`:

```ts
export type ImportErrorText =
  | { readonly key: MessageKey; readonly values?: MessageValues }
  | { readonly text: string };
```

and `lib/importErrorText.ts` renders it: `useImportError(error)` in a component,
`resolveDescribedError(t, error)` where a hook cannot go (`PendingDraftsList` calls it inside an `if`
branch that returns early; `ImportReviewPage` calls it in a `useCallback` that fires a toast).
`useAutosave` stores the unrendered `ImportErrorText` and resolves on the way out.

**`Error.message` holds the KEY**, not a translation — a translated log line is unsearchable and
depends on who happened to be looking at the screen.

**The `{ text }` variant is the deliberate opposite of §4's decision for the server.** There, a
pass-through variant was rejected because it would become the escape hatch that keeps German sentences
in handlers. Here it is not a loophole: the server's `message` arrives ALREADY localised (it negotiated
`Accept-Language`), and a library's `Error.message` genuinely has no key. It stays the minority path.

**An empty pass-through must fall back to a key** (`passThroughOr()`). `describeError()` hands
`toImportApiError()` `message: ""` for a shell `ApiError` carrying none, and `readJson()` synthesises
the same for an unparseable body; passing that through renders a blank headline — precisely the bare
"Fehler" this module exists to prevent. This was a real bug in the first draft of the port and
`importErrors.test.ts` caught it, which is the argument for that test: it walks every status/code
branch and asserts the key exists in BOTH catalogs. `tsc` cannot, because `{ text }` is untyped.

**Three placeholders keep GERMAN sample text in the English catalog**, and that is not an oversight:
`import.editor.minutes.placeholder` ("1 Std 15 Min") and the two section-heading examples ("Für den
Teig") name input that a German-only parser consumes (`parseDuration`, `INGREDIENT_HEADING_RE`). An
English example there would advertise input the parser silently drops. The sentence around it is
translated; only the sample token stays German.

### The language picker

`LanguageCard` on `/settings`, deliberately shaped like `AppearanceCard` — the same control over a
different axis, so the two read as one idea. Its description says out loud that it affects the
interface only, because the interface-vs-content distinction is invisible from the UI otherwise.

**`LocalePreference = Locale | "system"`, and `"system"` is a real third state.** Encoded exactly like
`ThemePreference`: **absent from `localStorage` means system**, so `setLocalePreference("system")`
REMOVES the key rather than storing a resolved locale, and the device keeps following
`navigator.languages` afterwards. Collapsing the two states would show "Deutsch" to somebody who has
never chosen anything and is only seeing German because their phone is — which is why the picker also
names what "System" currently resolves to.

`useLocalePreference()` registers a `languagechange` listener that acts ONLY while the preference is
`"system"`; re-resolving under an explicit choice would silently overrule the user. Firefox and Safari
do not always emit the event, so it is a best-effort improvement on the boot-time read, never the thing
correctness rests on.

**The `users.locale` PATCH sends the RESOLVED locale, never `null`** — that column exists only so mail
can pick a language, and the server cannot see `navigator.languages`. The cost is that mail goes stale
if the device language changes later while the preference is `"system"`; mail only, and it re-syncs the
next time the picker is touched. It stays fire-and-forget for the reasons in §6.

**The two language names are autonyms and identical in every catalog.** A user who has switched to a
language they cannot read needs a way back; `i18n.test.ts` pins both that and their presence in every
catalog.

### One real leak the audit's grep found

`services/groups/validation.ts` passed `"Eingabe ist ungültig"` as `validationFailed`'s **`details`**
argument, not its message argument — so it went onto the wire untranslated whatever the request asked
for, and no type error could catch it (`details` is `unknown` by contract). It also said nothing the
default message key does not already say in the negotiated locale. A non-Zod error now yields no
`details` at all. **This is the failure mode to look for when reading `i18n:check`'s output**: a
German string in a position the type system does not police.
